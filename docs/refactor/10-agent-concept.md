# Agent 概念辨析与本项目的 Agent 化

> 本文档回答两个问题：①"Agent 到底是什么"；②"本项目有没有 Agent"。
> 配合改造流程文档阅读：`00-tool-calling-flow.md`

## 一、Agent 到底是什么

### 字面与技术含义

- **字面**：Agent = 代理 / 智能体。一个能**自主行动**来完成目标的实体。
- **技术含义（LLM 语境）**：以 LLM 为"大脑"、工具为"手脚"、循环为"思考过程"，**能自主决定下一步做什么**的系统。

### Agent 的四个要素

| 要素 | 作用 | 类比 |
|------|------|------|
| **大脑（LLM）** | 理解、推理、决策 | 人的脑子 |
| **手脚（工具/动作）** | 与外部世界交互（检索、查库、调 API、执行代码） | 人的手脚 |
| **循环（ReAct）** | 思考→行动→观察结果→再思考的闭环 | 人"想想→做做→看看结果→再想想" |
| **自主权（autonomy）** | **自己决定**做什么、做几次、何时停 | 人自己拿主意 |

**第四点最关键**——这是区分 Agent 和"管道"的分水岭。

### Agent vs Pipeline（管道）的本质区别

```
Pipeline（管道/流水线）：
   步骤A → 步骤B → 步骤C → 步骤D    （流程写死，LLM 只是某一步的"填空机器"）
   特征：人（代码）决定流程，LLM 被动执行

Agent（智能体）：
   目标 → [LLM 决定做什么] → 做了 → [看结果，LLM 决定下一步] → ... → 完成
   特征：LLM 决定流程，代码只提供"手脚"和"把结果喂回去"
```

一句话：**Pipeline 里人是司机、LLM 是发动机；Agent 里 LLM 是司机、代码是车。**

## 二、怎么判断一个系统算不算 Agent

三个判定标准：

1. **有没有工具调用能力**（能行动）
2. **有没有循环**（能基于结果继续，不是一次性的）
3. **流程是不是 LLM 动态决定的**（自主权）

三者都满足 → Agent；只满足一两个 → "带 LLM 的管道" / "RAG 系统"，但不叫 Agent。

> 注意：很多人把"用了 LLM"就叫 Agent，这是营销话术，不准确。一个纯 RAG（问→检索→生成）是 Pipeline，不是 Agent。

## 三、本项目有没有 Agent

**诚实回答：改造前没有，改造后的主路径有了——但是个"弱 Agent"。**

### 改造前：纯 Pipeline，不是 Agent

改造前的 `SelfRagOrchestrator` 流程写死在 Java：

```
改写 → 必要性判断 → 检索 → 相关性判断 → 重排 → 草稿 → 支撑性判断
（7 步全写死，LLM 每步只被动回答 yes/no）
```

判定：
- ❌ 工具调用：无（Java 直接调 Service）
- ❌ 自主权：无（流程写死，LLM 不决定下一步）
- ⚠️ 循环：有迭代重试，但重试条件也是 Java 写死的

**结论：这是个"带 Self-RAG 优化的 RAG Pipeline"，不叫 Agent。**

### 改造后的主路径：是 Agent（弱 Agent）

改造后的 `orchestrateWithTools()`：

```
目标（回答用户问题）
  → [LLM 决定：要不要调 search_kb？] 
  → 调了 → 执行 → [LLM 看结果决定：够了？还是再查？] 
  → ... → [LLM 决定：信息够了，给答案]
```

判定：
- ✅ 工具调用：有（search_kb，原生 function calling）
- ✅ 自主权：有（模型自己决定调不调、调几次、何时停）
- ✅ 循环：有（ReAct 循环）

**结论：这是个 Agent。**

### 为什么说是"弱 Agent"

它满足了 Agent 的定义，但能力和自主权范围有限：

| 维度 | 本项目 Agent | 通用强 Agent（如 AutoGPT） |
|------|-------------|--------------------------|
| 工具数量 | 1 个（search_kb） | 几十上百个 |
| 行动范围 | 只能检索知识库 | 上网、写代码、调任意 API、操作文件 |
| 自主权范围 | 主要决定"检索与否/何时停" | 决定整个任务规划、拆解、执行 |
| 目标 | 单轮问答 | 复杂长任务（"帮我做个网站"） |
| 角色定位 | **检索增强问答的 Agent 化** | 通用任务自主完成 |

它是个**"垂直领域 Agent"**——在"知识库问答"这个窄场景里，把检索决策权交给了模型。这比写死的 Pipeline 好，但离大家想象中那种"啥都能干的 Agent"还很远。

### 降级路径：不是 Agent

`orchestrateLegacy()`（降级/静态编排）仍是改造点 4 的 Pipeline 逻辑，不是 Agent。它是 Agent 路径的安全网。

## 四、本项目的 Agent 化位置

```
LLM 应用的"Agent 化"光谱：

纯 RAG Pipeline ────── 弱 Agent ────── 强 Agent ────── 通用自主 Agent
（问→检索→生成）    （本项目改造后）              （AutoGPT/Devin）
                    ↑               （单领域多工具）    
              改造前在这里
              （写死的 Self-RAG）
```

本项目改造做的事：**把一个"写死的 Self-RAG Pipeline"向右推进到"弱 Agent"位置**。核心动作就是把检索决策权从 Java 代码移交给了 LLM。

## 五、准确回答

如果有人问"本项目有 Agent 吗"，准确的回答是：

> **有，但是个检索领域的弱 Agent。** 改造后的主路径（`orchestrateWithTools`）让 LLM 通过原生 function calling 自主决定何时检索知识库、检索结果不好时自己改写 query 再查、满意后直接生成答案——这构成了 ReAct 循环，符合 Agent 定义。但它只有一个工具（search_kb）、行动范围限于知识库检索，不是通用 Agent。
