# pomelo-ai 知识库文档管理与向量化 — 功能需求

> 基于 Dify / FastGPT / RAGFlow / MaxKB / Coze 五大主流知识库产品的调研，结合本项目现有架构（JDK21 + Spring Boot 4.1 + langchain4j 1.22 + Milvus 3.0 + Ollama nomic-embed-text 768维 + MinerU 4.0）梳理。
>
> 核心原则：**文档入库与向量化解耦**——上传后先解析提取保存原文，向量化作为可独立触发/批量调度的任务，不阻塞上传，不要求实时。

---

## 一、知识库管理

### 1.1 创建知识库

| 配置项 | 说明 | 默认值 |
|--------|------|--------|
| 名称 | 知识库显示名，必填 | — |
| 描述 | 知识库用途说明 | 空 |
| 嵌入模型 | 选择用于向量化的嵌入模型（当前 nomic-embed-text，768维） | nomic-embed-text |
| 向量维度 | 由嵌入模型决定，不可独立配（768） | 768 |
| 切片策略 | 通用切片 / 按标题层级 / QA问答对 | 通用切片 |
| 默认切片大小 | 每个切片的最大字符数 | 500 |
| 默认切片重叠 | 相邻切片共享字符数 | 50 |
| 默认 Top-K | 检索召回数 | 8 |
| 重排数量 | Rerank 后进入上下文的切片数 | 4 |
| 相似度阈值 | 低于此值的切片不召回 | 0.3 |
| 自动向量化 | 上传文档后是否自动触发向量化任务 | **关闭**（核心需求：手动/批量触发） |

### 1.2 知识库操作

- **编辑**：修改名称、描述、检索参数（Top-K/阈值/重排数）。修改检索参数不影响已索引的向量，只影响后续检索行为。
- **嵌入模型切换**：切换后已有向量维度可能不兼容，需**全量重新向量化**（提示用户确认）。
- **删除**：删除知识库 → 同步删除 Milvus Collection + MySQL 文档/切片记录 + 本地文件。二次确认。
- **统计概览**：文档数 / 切片数 / 向量数 / 总字符数 / 存储大小 / 向量化进度。
- **检索测试**：独立测试页，输入 query → 查看召回片段（含相似度得分、来源文档、页码），可临时调 Top-K/阈值/检索模式对比效果。

## 二、文档上传与解析

### 2.1 上传

| 能力 | 说明 |
|------|------|
| 支持格式 | PDF、DOC/DOCX、XLS/XLSX、PPT/PPTX、TXT、MD、CSV、HTML |
| 批量上传 | 支持多文件拖拽批量上传，单次上限 20 个文件 |
| 单文件限制 | 100MB（已配 `multipart.max-file-size: 100MB`） |
| 上传后状态 | `UPLOADED`（仅上传，未解析） |
| 存储位置 | 本地 `./data/uploads/{kbId}/{docId}/原始文件名`（已绑定到本机磁盘） |
| 重复检测 | 文件级 SHA-256 哈希，同库内相同哈希提示"文档已存在，是否重新上传" |

### 2.2 解析提取（与向化解耦）

上传后文档处于 `UPLOADED` 状态，**解析是独立步骤**，可手动触发或随向量化任务自动执行：

| 环节 | 说明 |
|------|------|
| 解析触发 | 手动单篇解析 / 批量解析 / 向量化任务自动先解析 |
| PDF 解析 | 文本型用 PDFBox；扫描件/复杂版面走 MinerU 4.0（OCR + 表格 + 版面布局） |
| Word 解析 | POI 提取段落 + 表格，表格转 Markdown |
| Excel 解析 | 逐 Sheet 提取，每行内容拼接，表头保留 |
| PPT 解析 | 逐 Slide 提取文本 + 备注 |
| 原文保存 | 解析后的纯文本保存到 MySQL `doc.parsed_content` + 本地 `parsed.txt` |
| 解析后状态 | `PARSED`（已解析，未切片） |
| 解析失败 | `PARSE_FAILED`，记录错误信息，可重试 |
| 内容预览 | 解析后可在文档详情页查看提取的纯文本内容 |

## 三、切片管理

### 3.1 切片策略

| 策略 | 说明 | 适用场景 |
|------|------|----------|
| 通用切片 | 递归字符分割（按段落→句子→字符逐级），可配大小/重叠 | 大多数文档 |
| 按标题层级 | 按 Markdown 标题(H1-H5)分段，保留层级结构 | 手册/论文/书籍 |
| QA 问答对 | 用 LLM 从内容生成"问题-答案"对，问题向量化 | FAQ/客服知识库 |
| 正则切片 | 用户自定义正则分隔符 | 编号条款/法律法规 |

### 3.2 切片操作

- **切片预览**：解析后切片前，可预览切片效果（每个切片内容 + 字符数 + 来源位置），不满意可调参数重新预览。
- **手动编辑**：切片生成后可增删改单个切片内容（标记为"已编辑"），编辑后的切片在向量化时以新内容生成向量。
- **切片元数据**：每个切片记录：来源文档 ID、来源页码/段落位置、切片序号、字符数、内容哈希（用于增量检测）。
- **切片状态**：`PENDING`（待向量化）/ `VECTORIZED`（已向量化）/ `FAILED`（向量化失败）/ `EDITED`（编辑后需重新向量化）。
- **重新切片**：修改切片参数后重新切分，旧切片标记为 `STALE`，向量化时只处理新增/变更的切片（增量向量化）。

## 四、向量化任务（核心）

### 4.1 任务模型

向量化是**独立可调度的异步任务**，不与上传/解析耦合：

```
文档状态机:
UPLOADED → PARSING → PARSED → CHUNKING → CHUNKED → VECTORIZING → INDEXED（可检索）
    ↘ PARSE_FAILED                    ↘ CHUNK_FAILED    ↘ VECTOR_FAILED
```

### 4.2 触发方式

| 方式 | 说明 |
|------|------|
| 单篇向量化 | 文档详情页点"开始向量化"，对该文档执行 解析→切片→嵌入→入Milvus 全流程 |
| 批量向量化 | 文档列表勾选多篇，点"批量向量化"，加入任务队列依次处理 |
| 全库向量化 | 知识库概览页点"向量化全部未完成文档"，处理所有 `UPLOADED/PARSED/CHUNKED` 状态文档 |
| 自动向量化 | 知识库级开关（默认关），开启后上传文档自动加入向量化队列 |

### 4.3 任务队列

| 能力 | 说明 |
|------|------|
| 队列模型 | FIFO 先进先出，支持优先级（手动触发 > 自动触发） |
| 并发控制 | 可配并发数（默认 1，避免 Ollama 嵌入过载），单文档串行处理 |
| 进度追踪 | 文档级进度（已完成切片数 / 总切片数），队列级进度（已完成文档数 / 总文档数） |
| 暂停/恢复 | 可暂停整个队列或单篇文档的处理，恢复后从断点继续 |
| 失败重试 | 单切片失败自动重试 3 次，仍失败则标记 `FAILED` 并记录错误，不阻塞同文档其他切片 |
| 批量限流 | 控制 Ollama 嵌入 API 调用频率（QPS 可配，默认 10 req/s） |

### 4.4 增量向量化

| 场景 | 处理方式 |
|------|----------|
| 新文档 | 全量向量化 |
| 切片内容编辑 | 只重新向量化被编辑的切片，删除旧向量 |
| 切片参数修改 | 重新切片，对比新旧切片内容哈希，只向量化新增/变更的切片 |
| 嵌入模型切换 | 全量重新向量化（维度可能变） |
| 文档删除 | 同步从 Milvus 删除该文档所有向量（按 `doc_id` filter 删除） |

### 4.5 向量化流程（单文档）

```
1. 状态置 VECTORIZING
2. 若未解析 → 先执行解析（PARSING → PARSED）
3. 若未切片 → 执行切片（CHUNKING → CHUNKED）
4. 逐切片调用 EmbeddingService.embedAll() 批量嵌入（nomic-embed-text, 768维）
5. 批量插入 Milvus（collection: pomelo_{kbId}）
   每条向量记录: id / vector / doc_id / chunk_id / page / content(输出字段)
6. 更新切片状态 PENDING → VECTORIZED
7. 全部完成 → 文档状态 INDEXED
8. 失败切片 → 重试3次 → 仍失败标记 FAILED
```

### 5.2 文档详情页

### 5.3 文档操作

| 操作 | 说明 |
|------|------|
| 重新解析 | 重新提取文本，覆盖旧解析结果，切片标记为 `STALE` 需重新切片 |
| 重新切片 | 用当前切片参数重新切分，增量对比只处理变更切片 |
| 重新向量化 | 删除该文档所有旧向量，全量重新向量化 |
| 删除 | 删除 Milvus 向量 + MySQL 切片记录 + 本地文件，二次确认 |

| 移动 | 跨知识库移动文档（需维度一致，否则需重新向量化） |

### 5.4 可配置元数据提取框架（核心设计）

> 不写死固定字段，而是提供**字段配置 + 自定义提取规则**的动态框架。字段可动态增删，每个字段有独立的"提取描述词"（规则），支持文档属性直取、正则匹配、LLM 生成三种提取方式。

#### 5.4.1 默认字段集（预置 13 项，可增删改）

| 字段 key | 字段名 | 数据类型 | 提取方式 | 提取描述词（规则示例） | 检索用途 |
|----------|--------|----------|----------|----------------------|----------|
| `file_name` | 文件名称 | string | 系统获取 | 上传时自动获取文件名 | 展示/过滤 |
| `title` | 标题 | string | 文档属性 | 从 PDF/Word 元数据 title 属性提取；无则取正文首行非空行 | 展示/加权 |
| `author` | 作者 | string | 文档属性 | 从文档元数据 author 属性提取；无则取正文"作者:xxx"模式匹配 | 过滤/溯源 |
| `org` | 机构 | string | LLM | 从文档内容提取署名机构/发布单位，可能出现在首页或末尾落款 | 过滤/溯源 |
| `publish_date` | 发布日期 | date | 文档属性+正则 | 优先从元数据提取；无则正则匹配正文中的日期(yyyy-MM-dd/yyyy年MM月dd日) | 时间过滤 |
| `publish_time` | 发布时间 | datetime | 文档属性 | 同上，带时分 | 排序 |
| `create_time` | 创建时间 | datetime | 系统 | 文档上传入库时间（系统自动记录） | 审计/排序 |
| `keywords` | 关键词 | list | LLM | 从文档内容提取5-10个核心关键词，反映主题，逗号分隔 | ⭐可向量化/标签过滤 |
| `summary` | 摘要 | text | LLM | 用200字以内概括文档核心内容 | ⭐可向量化/概览展示 |
| `topic` | 主题 | string | LLM | 判断文档所属主题分类，如"技术规范/管理制度/产品说明/研究报告" | 分类导航 |
| `terms` | 术语 | list | LLM | 提取文档中的专业术语，每个术语一行，排除常见词 | 专业检索增强 |
| `metrics` | 指标信息 | json | LLM | 提取文档中的关键指标(名称/数值/单位)，JSON 数组格式 | 数据分析 |
| `vector_status` | 向量化状态 | enum | 系统 | 文档当前向量化状态(UPLOADED/PARSED/INDEXED等) | 管理核心 |

#### 5.4.2 字段配置（知识库级）

每个知识库独立维护自己的字段配置（不同知识库可配不同字段集）：

| 配置项 | 说明 |
|--------|------|
| `fieldKey` | 字段唯一标识（如 `author`），用于存储和检索过滤 |
| `fieldName` | 字段显示名（如"作者"） |
| `fieldType` | 数据类型：string / text / number / date / datetime / list / json / enum |
| `extractType` | 提取方式：`SYSTEM`(系统自动) / `DOC_PROPERTY`(文档属性) / `REGEX`(正则匹配) / `LLM`(大模型生成) |
| `extractRule` | 提取描述词/规则：LLM 方式时为提示词模板；REGEX 方式时为正则表达式；DOC_PROPERTY 时为属性名 |
| `required` | 是否必填（必填字段提取失败时文档标记异常） |
| `searchable` | 是否参与检索过滤（true 则检索时可按此字段过滤） |
| `vectorized` | 是否将字段值向量化参与检索（**关键词/摘要建议开启**，正文+摘要双路召回） |
| `displayInList` | 是否在文档列表展示该列 |
| `sortOrder` | 列表展示顺序 |

#### 5.4.3 提取流程

解析后（文档状态 `PARSED`）触发元数据提取，**与切片/向量化独立**，可并行：

```
文档解析完成(PARSED)
    ↓
遍历知识库的字段配置
    ↓ 分发
┌─────────────────────────────────────────────────────┐
│ SYSTEM        → 直接取系统值(file_name/create_time/vector_status) │
│ DOC_PROPERTY  → PDFBox/POI 读取文档元数据(title/author/date)      │
│ REGEX         → 按自定义正则从 parsed_content 匹配                 │
│ LLM           → 用 extractRule 提示词调 qwen2.5:7b 生成            │
│                  (可合并多字段为一次 LLM 调用，降低成本)            │
└─────────────────────────────────────────────────────┘
    ↓
存入 document_metadata 表(doc_id, field_key, field_value)
    ↓
若字段 vectorized=true → 将字段值额外向量化(如摘要/关键词)
                         作为独立向量入 Milvus，检索时正文+摘要双路召回
```

#### 5.4.4 LLM 批量提取优化

多个 LLM 字段可合并为一次调用，降低成本：
```
提示词模板（合并 keywords + summary + topic + terms + metrics）：
"请分析以下文档内容，提取元数据并以 JSON 返回：
- keywords: 5-10个核心关键词，逗号分隔
- summary: 200字以内摘要
- topic: 主题分类(技术规范/管理制度/产品说明/研究报告/其他)
- terms: 专业术语列表
- metrics: 关键指标[{name,value,unit}]

文档内容：
{parsed_content}"

→ 1 次 LLM 调用提取 5 个字段，本地 qwen2.5:7b 约 3-8 秒
```

#### 5.4.5 动态增删字段

| 场景 | 处理 |
|------|------|
| 新增字段 | 在字段配置中加一条；对已有文档可选择"批量补充提取"（异步任务） |
| 删除字段 | 从字段配置删除；已有文档的该字段值保留但不再展示/过滤（或可选清理） |
| 修改提取规则 | 改 extractRule 后，对已有文档可选择"按新规则重新提取" |
| 启用/停用字段 | 停用的字段不再对新文档提取，旧值保留 |

#### 5.4.6 元数据在检索中的作用

| 用途 | 说明 |
|------|------|
| **过滤检索** | 检索时按元数据 filter（如 `author=张三`、`publish_date>=2024-01-01`），Milvus filter 表达式实现 |
| **向量增强** | `vectorized=true` 的字段（摘要/关键词）生成独立向量，检索时与正文向量并行召回，合并结果 |
| **列表展示** | 文档列表按 `displayInList` 字段动态展示列 |
| **分类导航** | 按 `topic` 字段分组浏览文档 |
| **溯源展示** | 回答引用时附带来源文档的元数据（作者/机构/发布日期） |

#### 5.4.7 文件夹目录（与元数据并行）

| 能力 | 说明 |
|------|------|
| 目录树 | 知识库内支持文件夹目录（MySQL 闭包模型存储父子关系） |
| 文档归类 | 文档可放入文件夹，也可不归类（根目录） |
| 与元数据关系 | 文件夹是物理组织，元数据是逻辑标签，两者并行互不冲突 |
