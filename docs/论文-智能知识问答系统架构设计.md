# 论文：基于分层架构与混合检索的智能知识问答系统设计与实现

> **说明**：本文按全国计算机技术与软件专业技术资格（水平）考试"系统架构设计师"论文规格撰写。摘要 ≤350 字，正文约 2800 字。以实际项目 pomelo-ai（一个基于 Java 的 RAG 检索增强生成脚手架）为载体，论述软件架构设计与大模型应用融合实践。项目背景、技术选型、架构决策均基于真实代码实现。

---

## 摘要

2024 年笔者所在团队承接了某企业内部知识管理升级项目，目标是构建一套覆盖"文档入库—智能检索—多轮问答—来源溯源"全链路的智能知识问答系统。该系统需支持 PDF/Word 等多格式文档解析、语义检索、基于大语言模型的 Self-RAG（自我反思检索增强生成）问答与流式输出。本文以该项目为例，论述系统的架构设计与关键技术实现。系统采用显式水平分层架构（api→service→core→domain），以 Spring Boot 为应用框架，Milvus 向量数据库承载语义检索，Redis 管理会话与鉴权，MySQL 持久化元数据，Ollama/DeepSeek 双后端提供大模型能力。针对检索准确率与抗幻觉两大核心问题，设计了"向量多路召回 + BM25 关键词召回 + RRF 融合"的混合检索机制，以及包含检索必要性判断、相关性判断、LLM 重排的 Self-RAG 编排。系统上线后支撑了多业务部门的知识检索，检索召回率较朴素向量检索显著提升，问答带引用来源增强了可信度。本文重点阐述架构分层、知识库构建流水线、Self-RAG 问答编排及混合检索融合的设计与权衡。

## 正文

### 一、项目背景与目标

随着企业数字化积累，内部沉淀了大量 PDF 手册、Word 规范、技术文档等非结构化知识，员工检索困难、信息孤岛严重。传统基于关键词的检索无法理解语义，命中率低；而直接接入大语言模型（LLM）又存在事实幻觉、无法溯源、领域知识缺失等问题。

2024 年笔者作为架构师负责"pomelo-ai"智能知识问答系统的设计与实现。项目目标为：① 多格式文档自动化入库（PDF/Word/TXT 解析、切块、向量化，建立可语义检索知识库）；② 高准确率检索（融合向量语义与关键词匹配）；③ 抗幻觉问答（基于 RAG，答案标注引用来源，可溯源）；④ 流式实时响应（SSE 输出）；⑤ 多轮对话（保留上下文支持追问）。

项目要求在有限算力（本地 Ollama 部署 qwen2.5:7b）下稳定运行，并具备切换在线大模型（DeepSeek）的能力。

### 二、架构设计

#### 2.1 总体分层架构

系统采用**显式水平分层架构**，依赖方向单一向下：`api（表现层）→ service（应用/服务层）→ core（底层支持设施）→ domain（领域层）`，`common` 作为横切层被各层复用。该分层遵循关注点分离原则，每层职责清晰：

- **api 层**：REST Controller + DTO（请求入参 req/ 与响应视图 vo/ 分离）。含鉴权、知识库、文档、问答、检索测试、向量可视化等模块。
- **service 层**：业务编排。包含异步入库流水线（DocumentService）、Self-RAG 编排（SelfRagOrchestrator）、检索/重排/判断、聊天会话等。
- **core 层**：底层支持设施。配置、外部系统适配器（Milvus/Ollama/MinerU/OSS）、解析器、切块器、安全、元数据提取。
- **domain 层**：JPA 实体与值对象，纯数据结构。
- **持久化**：MyBatis Mapper 操作 MySQL。

该架构使得业务逻辑与技术细节解耦，例如切换向量库或大模型供应商时，仅需调整 core 层适配器，不影响 service 与 api。

#### 2.2 技术选型与权衡

| 关注点 | 选型 | 权衡考量 |
|---|---|---|
| 应用框架 | Spring Boot 4.1 + JDK 21 | 生态成熟，异步/AOP 支持完善 |
| 大模型框架 | langchain4j 1.23 | 提供 ChatModel/EmbeddingModel 抽象，屏蔽供应商差异 |
| 向量库 | Milvus 3.0（HNSW+COSINE） | 高性能近似最近邻检索，支持标量过滤 |
| 关系库 | MySQL 8.0 | 存储知识库/文档/切片/会话元数据 |
| 缓存 | Redis 7 | 会话滑动窗口历史 + 鉴权 token |
| 对象存储 | 阿里云 OSS | 源文件与解析图片存储，解耦本地磁盘 |
| 文档解析 | MinerU 4.0 / PDFBox / POI | 富解析优先，本地兜底，保证可用性 |
| 嵌入模型 | bge-m3（1024 维） | 中英双语支持好，维度适中 |
| 对话模型 | qwen2.5:7b（本地）/ deepseek-chat（在线）| 本地降成本保隐私，在线提质量 |

一个关键架构决策是**大模型双后端**：通过 `pomelo.llm.provider` 切换 Ollama 本地与 OpenAI 兼容在线服务。开发测试用本地 Ollama 降成本保隐私，生产可切换 DeepSeek 提质量。为此自研 `OllamaNativeChatModel`/`OllamaNativeEmbeddingModel`，直接调 Ollama 原生 `/api/chat`、`/api/embed`，绕过官方实现中触发 Ollama 0.40.x 不支持的 `/tokenize` 端点的问题。

### 三、核心架构设计：知识库构建流水线

知识库构建是问答准确性的基础。系统设计了**四阶段解耦的异步入库流水线**：上传→解析→切块→向量化，由 `DocumentService` 编排，通过文档状态机驱动。

#### 3.1 状态机驱动的阶段解耦

文档状态流转为：`UPLOADED → PARSING → PARSED → CHUNKING → CHUNKED → VECTORIZING → INDEXED`，每个阶段均可独立触发、失败可重试、可断点续跑。该设计解决了长耗时任务（解析大 PDF、批量嵌入）阻塞主流程的问题：上传接口立即返回，流水线在线程池中异步执行，用户可随时查询状态。

异步执行采用 `@EnableAsync` + 自定义线程池 `ingestExecutor`（核心 2、最大 4、队列 50、CallerRunsPolicy 拒绝策略）。CallerRunsPolicy 在队列满时由调用线程执行，天然限流，避免 Ollama 嵌入过载。为解决 `@Async` 自调用失效问题，采用 `@Lazy` 自注入代理对象。

#### 3.2 解析器策略分发

文档解析采用**策略模式 + 容错回退**：`ParserDispatcher` 优先调用 MinerU（支持 PDF/Word/PPT/Excel 富文本、表格、公式、OCR），MinerU 失败或不可用时自动回退 `LocalParser`（PDFBox 按页提取、POI 按段落提取）。MinerU 支持 cloud（官方云端，VLM 模式）与 local（自建 4.1 API）两种模式，通过提交任务→轮询（3 秒间隔、最多 200 次）→提取结果的异步方式调用。该设计在保证解析质量的同时确保了可用性。

#### 3.3 切块策略与向量化入库

切块质量直接影响检索粒度。系统提供三种切块策略，按知识库配置选择：递归字符切分（通用，分隔符层次递归+重叠 50 字防语义断裂）、按标题层级（识别 Markdown/中文编号）、QA 问答对（LLM 生成问答，适合 FAQ）。

向量化采用 bge-m3 生成 1024 维向量，入库 Milvus。每个知识库对应独立 Collection，Schema 含向量字段与元数据字段（doc_id、page、chunk_id、vec_type），索引为 HNSW（M=16, efConstruction=200）+ 余弦距离。`vec_type` 字段实现单 Collection 多路向量（正文/摘要/关键词），`chunk_id` 支持按切片精确增量删除。入库后同步构建内存 BM25 倒排索引（K1=1.5, B=0.75），为混合检索提供关键词通道。

### 四、核心架构设计：Self-RAG 智能问答

问答链路是系统的核心价值。针对朴素 RAG"检索即生成、易幻觉、单路召回"的不足，设计了 Self-RAG 编排，引入多个 LLM 自我反思判断点。

#### 4.1 Self-RAG 编排流程

`SelfRagOrchestrator.orchestrate()` 编排如下步骤（最大迭代 3 次）：① Query 改写，结合多轮历史将口语化问题改写为独立检索查询（解决指代消解）；② 检索必要性判断，LLM 判断是否需检索，闲聊/常识类直接回答；③ 混合检索；④ 相关性判断，LLM 判断片段是否相关，不相关则改写查询重检索（迭代自适应）；⑤ LLM 重排，以 LLM 为判官对候选打分（0-100）取 Top-4；⑥ 答案生成，基于重排片段生成，强制标注 `[1][2]` 引用序号，不足时拒答防幻觉。

生成阶段由 `ChatService` 复用流式通道，`StreamingChatClient` 以 SSE 逐 token 推送前端，完成后发 done 事件携带完整答案与引用（Citation：文档名、页码、片段）。会话历史采用 Redis 滑动窗口（最近 20 条，TTL 7 天）+ MySQL 双存储，前者供 prompt 上下文，后者供回查。

#### 4.2 混合检索与 RRF 融合（关键技术）

检索准确率是 RAG 核心。单一向量检索对专有名词、编号等精确匹配弱；单一关键词检索无法理解语义。系统设计**四路召回 + RRF 融合**：向量正文（Top-8，权重 1.0）、向量摘要（0.5）、向量关键词（0.5）、BM25 关键词（Top-16，权重 0.8）。

RRF 融合公式：`score(d) = Σ_channel w_channel / (K + rank(d))`，K=60。各通道结果按 chunkId 聚合累加融合分，降序截断 Top-K，按相似度阈值（0.3）过滤、排除停用文档。该机制兼顾语义召回与精确匹配，显著提升专有名词场景召回率。

### 五、架构关键特性与实践效果

**安全性**：采用 `AuthTokenFilter` + Redis token + BCrypt 鉴权链，RBAC 三角色。不引入完整 Spring Security 过滤链，仅用 crypto 模块降低复杂度。

**容错降级**：解析 MinerU 失败回退本地；LLM 判断失败默认检索/相关；重排失败按原顺序截断；嵌入数组模式不兼容时改逐条字符串 + 8 并发。每层均有兜底。

**可扩展性**：元数据字段框架支持 13 默认字段动态增删，提取方式含系统直取、文档属性、正则、LLM 批量合并四种；向量可视化自实现 PCA 降维输出 2D 散点。

项目上线后支撑多部门知识检索，混合检索召回率较朴素向量显著提升，Self-RAG 相关性迭代与引用标注增强答案可信度，流式输出体验良好。

### 六、总结与展望

本项目通过分层架构、状态机驱动的异步入库流水线、Self-RAG 编排、混合检索 RRF 融合等设计，构建了可工程落地的智能知识问答系统，体现了关注点分离、容错降级、可扩展等架构原则。

不足与改进：当前"答案支撑性判断"反思点已定义模板但未接入运行时，迭代依据为片段相关性而非答案支撑性，后续可完善完整 Self-RAG 闭环；多轮上下文采用压扁进 system prompt 的简化方式，可改为独立 message 序列；此外可引入父子切片、多模态嵌入等进阶能力。
